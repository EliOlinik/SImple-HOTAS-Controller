# T08 – DeviceToggler (code done, not yet run on real hardware)

## Added
- `Core/ToggleTargets.cs` (+ `ToggleTargetsTests`): which nodes to switch for a controller.
- `Win32/DeviceToggler.cs : IDeviceToggler` – ctor `(IDeviceService, ISafetyPolicy, IDisabledStateStore)`. Flow: refetch controller -> safety policy -> SetupAPI `DIF_PROPERTYCHANGE` (`DICS_DISABLE`/`DICS_ENABLE`, `DICS_FLAG_GLOBAL`) per target node -> poll `CM_Get_DevNode_Status` up to 5 s -> update state store. Partial disable is rolled back. "Access denied" is reported as "run as administrator".
- `DeviceEnumerator.GetInstanceId/IsDisabled/HidClassGuid` made `internal` for reuse.
- Dump tool: `--disable <name>` / `--enable <name>` with a typed-YES confirmation. Needs an elevated terminal.

## Manual test (user only – agents must not run this)
In an elevated terminal, on a non-essential controller (suggested: DualSense):
1. `dotnet run --project tools/HotasController.Dump -- --disable "DualSense"` -> type YES. Check Device Manager / Windows "Set up USB game controllers" (joy.cpl).
2. Re-run the dump: controller should show enabled=False and still be listed.
3. `... -- --enable "DualSense"` -> type YES; controller works again; state file record removed.
Also try: replug while disabled, and disabling while a game/joy.cpl has it open.

## Known gaps
- Not run on real hardware yet. Open question: whether a disabled controller is still recognised by the "game controller" name fallback (unit-tested only).
- A node needing a restart is only detected through the verify timeout, not via DI_NEEDRESTART.
- Win32 layer has no automated tests (tests reference Core only).

## Hardware test findings (2026-11-07, DualSense, Steam + joy.cpl open)
- Global-scope disable: device vanishes briefly, `SetupDiCallClassInstaller` fails with ERROR_INVALID_DATA, device returns. Hardware-profile scope: reports OK but changes nothing.
- After these attempts the node `USB\VID_054C&PID_0CE6&MI_03\...` had status 0x180210A, i.e. `DN_NEED_RESTART` (0x100) set; `pnputil /disable-device` then refuses: "Device is pending system reboot to complete a previous operation".
- Working theory: another process (Steam / joy.cpl) keeps the device open, so Windows cannot stop the stack, rolls back and flags a pending restart. Unconfirmed until retested after a reboot with those programs closed.
- Toggler now: verifies each scope (1.5 s) before accepting it, reports a status timeline on failure, and refuses early with a clear message if a target node has `DN_NEED_RESTART`.
- Open design risk: games and Steam routinely hold controllers open, so a PnP disable may often need them closed. If it keeps failing, consider alternatives (disable the HID child node instead, or hide the device per-app).

## Update after reboot retest
- With Steam + joy.cpl open, `pnputil /disable-device|/enable-device` and the tool's `--disable` work after a Windows restart (the earlier failures were the pending-restart flag).
- `--enable` initially found no controller: disabling the USB-level node removes the HID child, so the disabled device had no game-controller usage/name. Fixed: `GameControllerGrouper.Group(nodes, disabledByApp)` keeps groups listed in the state file that still have a disabled node and flags them `GameController.RecognisedFromState`; `DeviceSafetyPolicy` accepts those (enable only). `DeviceService(store)` supplies the set. T10 must construct `DeviceService` with the shared `DisabledStateStore`.
- Known gap: a record stays in the state file if the user re-enables outside the app (e.g. pnputil). Harmless (ignored while the device is enabled) but should be pruned during startup recovery (T11).
- Controllers disabled outside the app (Device Manager) are not recognisable while disabled.
